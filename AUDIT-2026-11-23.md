## Medium

### M-01 `panicWith` callable by anyone on an EIP-7702-delegated EOA
- Location: `PanicRevoke.panicWith` (L~290).
- Impact: while an EOA is delegated to PanicRevoke, any third party can call `panicWith` on it with arbitrary targets and make the EOA call `approve(x, 0)` on any contract, Permit2 `lockdown`, and SpendPermission `revoke`. This revokes approvals the owner never registered (griefing of live agent/DeFi positions). With a no-return-tolerant approve (needed for M-02), the same path would let an attacker call `approve(attacker, 0)` on an ERC-721 and take NFT #0; today that is only blocked by accident (bool decoding).
- Proof: `test_H01_strangerCannotRevokeArbitraryApprovalsOn7702Eoa`, `testFuzz_H01_onlySelfCanPanicWith`, `test_H01_strangerCannotPanicWithOn7702Eoa_nftTheft` (all failed/were exploitable before the fix).
- Fix: if `address(this)` carries a 7702 designator (`0xef0100…`), require `msg.sender == address(this)`; new error `NotAuthorized`. The delegatecall path is unchanged (the calling account contract authorised it). Status: **Fixed**.

### M-02 USDT-style tokens (approve returns nothing) make `panic()` / `panicWith()` revert
- Location: `_executeAsAccount` (`IERC20(token).approve(spender, 0)`).
- Impact: Solidity decodes a `bool` return, so mainnet USDT and similar tokens revert the whole panic. The panic button fails exactly when needed.
- Proof: `test_M01_panicHandlesNoReturnApprove` (reverted before fix). Known pattern (audit-kb: Sushi/Cantina 40878, AXION/Sherlock 43535).
- Fix: low-level `_approveZero` accepting empty or `true` return data. Status: **Fixed**.

### M-03 All-or-nothing panic: one failing target blocks every revoke
- Location: `_executeAsAccount`, `_executeAsModule`, `_moduleCall`, `_prevModule`.
- Impact: a single paused/broken token, a reverting manager call, or a Safe module the owner already disabled by hand (still registered) reverts the entire `panic()` / `panicAsModule()`, leaving all other approvals live during an incident.
- Proof: `test_M02_revertingTokenDoesNotBlockAccountPanic`, `test_M02_failingModuleCallDoesNotBlockSafePanic`, `test_M02_staleModuleDoesNotBlockSafePanic` (reverted with `paused` / `ModuleCallFailed` / `UnknownTarget` before fix).
- Fix: best-effort execution: each failed revoke is skipped and logged as `RevokeFailed(account, kind, target, index)` (kind 0 ERC-20, 1 Permit2, 2 SpendPermission, 3 module). `_prevModule` returns `(found, prev)`. A SpendPermission whose `account` mismatches still reverts (invalid input). Status: **Fixed**.

### M-04 Reentrancy lock writes the account's persistent storage slot 8
- Location: `nonReentrant` / `_locked` (storage slot 8).
- Impact: `panic()` runs in the account's context (7702 or delegatecall), so the lock does `sstore(8, 1)` then `sstore(8, 0)` on the *account's* storage: whatever the wallet (or a previous 7702 delegate) kept in slot 8 is zeroed, and if it held exactly `1` the panic always reverts with `Reentrancy()`.
- Proof: `testFuzz_M03_panicDoesNotTouchAccountStorage` (slot clobbered before fix), `test_M03_slot8EqualOneDoesNotBrickPanic` (reverted before fix).
- Fix: lock moved to transient storage (`tload`/`tstore`, slot `keccak256("PanicRevoke.lock") - 1`; Cancun is live on Ethereum and Base). Status: **Fixed**.

## Low

- **L-01 `panic()` on a 7702 EOA is permissionless.** Anyone can trigger the owner's *registered* revokes at any time (griefing only; targets were chosen by the owner). Same model as `panicAsModule`. Status: Acknowledged, documented in README.
- **L-02 `encodeRevokeCalls` uses `SENTINEL` as `prevModule` for every module.** Correct only for the first module in the Safe list; the dapp must compute `prev` itself (comment says "hint"). Status: Acknowledged.
- **L-03 Residual authority outside scope.** Permit2 `lockdown` does not void already-signed SignatureTransfer permits; EIP-7702 delegation can only be cleared by a type-4 tx. Documented in NatSpec/README. Status: Acknowledged.
